# 测试方法手册（持续迭代）

> **定位**：本手册是 AGENTS.md §5.1（连续运行验证）的展开与积累，记录"失效机制 → 应对技巧"的对应关系。
> **维护约定**：每次发现新的失效模式或验证技巧，按文末模板追加一条。**每条必须回答"为什么有效"，
> 且论证必须落到失效机制或本项目实测数据上**，不允许"经验上应该这样"。
> **使用约定**：写测试前扫一遍「触发问题清单」；遇到 bug 先到「失效案例表」查类别；每个技巧都附

## 二、策略层技巧

### T2. 递进验证：冒烟 → 小批次 → 全量
- **针对的失效**：单次通过就宣布完成，批量使用时崩溃或结果漂移。
- **为什么有效**：三类失效（状态残留、逐项隔离缺失、累积效应）只在"多次/多样"的前提下触发；
  递进结构让每次升级的成本都建立在上一步全绿之上，失败时能把问题域缩小到最近一次升级引入的维度。
- **本项目实证**：2026-09-07 推理验证。Tier-1 单对通过 → Tier-2 第 1 对即整机崩溃（每启动只
  能推理一次的 P0 缺陷），8 月的一次性验收从未暴露它。Tier-3 全量 126/126 通过后才能对性能
  下结论（中位 0.91s/对）。
- **执行要点**：第一级做通核心链路；第二级 ≥3 组且必须包含"上一次失败过的输入"；全量放后台。
- **何时可省**：纯函数级改动且无任何持久状态时，单元层重复执行即可替代。

### T3. 连续运行验证（重复执行；行业检索词：state leak / pass-then-rerun）
- **针对的失效**：进程内持久状态——连接池、锁文件、临时目录、单例、缓存、静态计数器——只在
  **第二次**使用时暴露污染。
- **为什么有效**：它直接构造了失效的触发前提（第二次执行）。第一遍是"功能是否正确"的测试，
  第二遍是"上一遍是否清理干净"的测试，两者检验的是不同的代码性质，后者没有前者不可替代。
- **本项目实证**：EPIPE 崩溃的机理是健康检查在首次长推理期间留下陈旧连接，worker 处理完才
  accept 到它——单次验收永远走不到这条路径。
- **执行要点**：修复类改动必须"同输入连跑两遍"；第二遍的通过标准与第一遍完全一致。

### T11. 故障注入 / 混沌（行业检索词：chaos engineering、fault injection，出处 Netflix Chaos Monkey）
- **针对的失效**：容错代码只在故障真实发生时被执行；"有 try/except"不等于"异常路径正确"。
- **为什么有效**：直接把系统置于故障态观察行为，等价于枚举了故障场景；比代码评审更能发现
  "异常被捕获但处理错误"（如吞掉后进入错误状态）的问题。
- **本项目实证**：entrypoint 监督循环的验证方式就是 `kill -9` worker 进程，观察 8 秒内自动
  拉起、容器存活——比走查 shell 脚本可靠得多（实际上走查就漏掉了 `set -e` 导致循环自杀的问题）。
- **执行要点**：注入点选"依赖进程、网络、磁盘满"三类；每次注入后必须验证**恢复能力**而非仅
  仅是"没崩溃"。

### T10. 浸泡测试（行业检索词：soak testing、endurance testing）
- **针对的失效**：内存泄漏、句柄/文件描述符泄漏、磁盘缓慢增长、日志膨胀——全部随时间线性或
  阶梯增长，短时测试数学上不可见。
- **为什么有效**：泄漏速率 × 时长 > 噪声才能观测，浸泡把时长拉到阈值以上。
- **本项目状态**：未实施。触发条件：出现需要连续运行数小时以上的场景（如定时任务、常驻推理
  服务高频调用）时立项。全量 Tier-3（126 次连续推理）已是其雏形——显存峰值全程稳定 2.26GB
  无增长，即是一次小型浸泡的结论。

## 三、用例设计层技巧

### T6. 等价类划分 + 边界值分析（行业检索词：equivalence partitioning、boundary value analysis）
- **针对的失效**：输入域无限，测试必然是采样；缺陷在边界聚集（off-by-one、空/满、阈值两侧）。
- **为什么有效**：等价类把无限域压缩为有限代表集，解决"测不完"；边界值之所以是优先采样点，
  是因为边界两侧常走不同代码分支（`<` 与 `<=`、空集合与单元素），分支覆盖差异即缺陷密度差异。
- **本项目实证**：推理 `limit` 参数（0=不限，N=前 N 个）与 KML 过滤的空交集路径，都是典型边界。
- **执行要点**：每个数值参数至少取：最小、最小+1、正常值、最大-1、最大、越界各一。

### T7. 数据真实性测试（行业检索词：production-like test data）
- **针对的失效**：代码对数据分布的**隐含假设**（格式唯一、字段必填、编码一致）不会体现在手工
  构造的规整数据里。
- **为什么有效**：真实数据的多样性直接攻击隐含假设；合成数据只会"验证代码实现了作者以为的规格"。
- **本项目实证**：权威 348 条 TBBH 实际存在 C 前缀（143）/ZJ 前缀（119）/CT 前缀（81）/纯数字
  （5）四种格式；用 `Mine.csv` 的编号（非权威源）做搜索必然失败。若测试只用单格式造数，格式
  处理缺陷永远不可见。
- **执行要点**：测试数据从权威资产生成；发现格式分叉时，每个等价类至少一条真实样本进固定用例。

### T8. 异常路径与负面用例（行业检索词：negative testing、error path）
- **针对的失效**：异常分支的代码量与缺陷密度成正比，但用户少走、开发者少测——双重覆盖不足。
- **为什么有效**：异常路径的失败模式（静默吞掉、错误码丢失、状态半更新）无法被正常路径用例触发。
- **本项目实证**：错误密码测试（红色"账号或密码错误"正确显示）；worker 对已断开客户端的响应
  写入失败后**记日志并继续服务**——"明确失败但不伤服务"是异常路径的设计契约。
- **执行要点**：每个外部交互（登录、上传、API 调用）至少三条负面用例：空输入、错误凭证、中断。

### T9. 并发与竞态（行业检索词：race condition、concurrency testing）
- **针对的失效**：竞态的触发依赖特定时序交错，串行测试在概率上永远碰不到。
- **为什么有效**：并发压测把时序交错的概率放大到可观测；竞态一旦在测试中出现，几乎必然可稳定
  复现（时序窗口通常由代码结构决定，不是纯随机）。
- **本项目实证**：miner-api 的 `kmlInferenceActive` 锁使第二个并发推理请求得到明确 409——
  这是"并发时行为可预期"的正例。
- **执行要点**：优先验证"是否有锁/队列"这一结构事实，再决定是否需要压测工具。

## 四、工程与工具层技巧

### T12. 回归墓碑（行业检索词：regression test；红-绿重构的第一步）
- **针对的失效**：修复过的 bug 在重构/回滚/合并中复活——没有测试守卫，复活是静默的。
- **为什么有效**：测试把"bug 曾存在的条件"固化为可执行断言；修复代码被误删时测试变红，等于
  给修复上了保险。这也是 AGENTS.md"先复现定位根因 → 写失败测试 → 最小修复"流程的最后闭环。
- **本项目实证**：EPIPE 修复附带 `test_survives_client_disconnect_before_response`——修复前
  它在旧代码上红（复现 BrokenPipeError），修复后绿。任何人删掉 send 守卫，CI 立即变红。
- **执行要点**：回归测试必须在**未修复的代码上先跑红**，否则它没有证明力（可能永远绿）。

### T13. 环境一致性（行业检索词：test environment parity）
- **针对的失效**：宿主机与部署环境的依赖/内核/文件系统差异，导致"测试通过但部署失效"或相反
  ——测试结论在错误的环境里失去效力。
- **为什么有效**：测试的价值命题是"此处通过 ⇒ 彼处通过"，环境不等价则命题不成立。
- **本项目实证**：worker 的 AF_UNIX socket 测试在 Windows 宿主机结构性不可运行（24 个
  ModuleNotFoundError + AF_UNIX 缺失），而容器内 112 个测试全绿——容器才是权威测试环境，
  宿主机套件仅作冒烟。
- **执行要点**：明确每个测试套件的权威环境并写进文档；平台相关用例用 skipUnless 显式标注。

### T14. 先测量后优化（行业检索词：profiling before optimization；"premature optimization"）
- **针对的失效**：性能直觉在缓存/IO/冷启动面前系统性失准，优化错对象浪费时间还引入风险。
- **为什么有效**：分阶段计时把"慢"分解为可归因的构成，优化对象从猜测变为测量结论。
- **本项目实证**：体感"推理偏久（30~40 秒）"，打点后发现暖跑 inference 仅 3.5s（占 93%）、
  全量中位 0.91s——真正的问题是崩溃导致的反复冷启动，不是 GPU 慢。若无打点，会把优化精力
  错投到批处理/并行上。
- **执行要点**：先加分阶段计时（一次提交的纯增量），跑真实负载拿到分布（中位数比平均值抗
  离群），再决定是否优化、优化哪段。

### T15. 测试中的敏感信息管理
- **针对的失效**：测试日志、截图、CI 输出、临时文件是常被遗忘的泄露面；AGENTS.md 明令禁止
  密码入日志/文档/提交。
- **为什么有效**：泄露面的本质是"敏感值流入了持久化介质"；对策必须逐介质切断（内存变量直用、
  临时文件用后即删、断言只输出布尔/长度不输出内容）。
- **本项目实证**：管理员密码经剪贴板→失败（剪贴板随进程退出清空），改为临时文件→浏览器内存
  变量→`fill()` 注入→立即删除；期间所有校验只输出布尔值，密码零回显。
- **执行要点**：设计涉及凭证的测试时，先画出值的流向图，确认每个落点要么不持久、要么即用即删。

### T16. 工具限制与产品缺陷的隔离
- **针对的失效**：自动化测试失败后直接当 bug 修，浪费工时甚至改坏正确代码；反过来，真缺陷被
  "工具问题"一句话掩盖。
- **为什么有效**：区分两者的判据是**替代路径验证**——换一种驱动方式（坐标点击替代语义点击、
  人工操作替代脚本）若行为正确，则工具嫌疑上升；同时排查应用的可疑构造（全局动画、透明覆盖层）。
- **本项目实证**：Playwright 对全部按钮语义点击超时，但坐标点击、人工交互全部正常，且源码无
  全局动画——结论记为工具限制，未做任何"修复"。
- **执行要点**：结论必须写明证据（做了哪些替代验证）；工具限制要记录在案，避免下次重查。

### T17. 满屏页面滚动验证（overflow 审查）
- **针对的失效**：为全屏地图/大屏设计的全局样式（`html,body{overflow:hidden}` + 100% 高度外壳）
  会让后加的普通页面在内容超过一屏时被**静默裁剪**——不报错、内容不可达、页面不可滚。
- **为什么有效**：滚动缺陷无法靠"页面能打开、数据正确"发现，只有**实际执行滚动动作**才暴露；
  且全局 overflow 样式总是先于内容页存在，属于结构性埋雷，内容一多必然触发。
- **本项目实证**：项目工作台（348 矿山列表）无法滚动（2026-09-08 协作者使用时暴露）；
  根因即 index.html 全局 `overflow:hidden` + `.app-shell height:100vh`，修复为工作台页面
  自带滚动容器（`height:100vh; overflow-y:auto`）。
- **执行要点**：每个独立页面实测"滚到底 + 滚回顶"；把窗口高度调小（如 768px）复测；
  检查点不止"能滚"，还包括"滚到的底部内容完整、可交互"。
- **何时可省**：确认单屏展示、无内容溢出可能的页面。

### T18. 渲染取证：截图失效时的 DOM 状态核验（行业检索词：visual debugging；DOM forensics）
- **针对的失效**：视觉验证依赖截图，但截图后端本身会失真（合成伪影、拼接错位、捕获直接失败）；
  只看截图会把"截图坏了"误判成"页面坏了"，或反过来掩盖真实渲染缺陷。
- **为什么有效**：最终渲染 = DOM 状态 + 浏览器合成。DOM 状态可以程序化取证，绕过合成环节：
  图层元素计数与 src、SVG path 的 `d` 属性长度、`elementFromPoint` 命中测试、把图片/瓦片
  画进 canvas 解码像素均值。逐层比对就能定位"哪一层画错/没画"，比人眼比对截图精确得多。
- **本项目实证**（2026-09-09 离线底图黑屏）：截图全黑，但取证显示瓦片 `img.leaflet-tile-loaded`
  30 张、直连 fetch 200、瓦片像素均值 RGB[59,73,39]（真实植被影像）→ 影像正常，是"被上层盖住"；
  再查遮罩 pane 的 path `d` 仅 33 字符（只剩世界矩形外环）→ 孔洞环丢失 → 锁定坐标轴未翻转。
  另：截图右侧/底部重复条带是捕获合成伪影，DOM 测量（元素矩形）与截图坐标不一致即暴露。
- **执行要点**：截图异常时先 DOM 取证再下结论；canvas/地图类内容必须解码像素验证，
  不能只看元素存在或网络 200；`elementFromPoint` 回答"这一点上最顶层是谁"。

### T19. 测试解释器钉死（行业检索词：test environment parity；interpreter drift）
- **针对的失效**：验证门命令里的裸 `python`/`node` 指向随时间漂移的宿主机环境——新装了别的
  版本、依赖被升级（如 flask_sqlalchemy 3.x 移除 `BaseQuery`）、 PATH 顺序变化。同一命令
  昨天全绿今天报 25 个 import error，看似代码回归实为环境漂移，反向掩盖真回归。
- **为什么有效**：验证门结果 = 代码 × 解释器 × 依赖矩阵 三元乘积；代码不变而其余两项漂移时，
  只有把解释器和依赖钉到与生产一致，门的红绿才只反映代码。
- **本项目实证**（2026-09-09）：同一 `unittest discover` 在宿主机 C:\Python314（无 flask）、
  Python310（flask_sqlalchemy 过新）、Miniconda 三个环境给出三份不同的失败清单；切到与
  镜像一致的 MMSeg310 conda 环境 116 个测试全绿——main 代码从未坏过。
- **执行要点**：验证门文档必须写明解释器来源（绝对路径/容器+环境名）；跨环境出现"不可能的
  失败"时，第一反应是换权威环境复跑，而不是开始改代码。
- **何时可省**：验证门已在容器/CI 内固定解释器运行的项目。

## 五、失效案例速查表

| 案例（2026-09-07） | 表象 | 根因失效类别 | 命中的技巧 |
|---|---|---|---|
| 推理 worker EPIPE 崩溃 | 每次启动只能推理一次 | 状态残留（陈旧连接）+ 放大器（wait -n） | T3、T2、T11、T12 |

> **定位**：本手册是 AGENTS.md §5.1（连续运行验证）的展开与积累，记录"失效机制 → 应对技巧"的对应关系。
> **维护约定**：每次发现新的失效模式或验证技巧，按文末模板追加一条。**每条必须回答"为什么有效"，
> 且论证必须落到失效机制或本项目实测数据上**，不允许"经验上应该这样"。
> **使用约定**：写测试前扫一遍「触发问题清单」；遇到 bug 先到「失效案例表」查类别；每个技巧都附
> 行业通用名称，可直接用于外部检索。

## 二、策略层技巧

### T2. 递进验证：冒烟 → 小批次 → 全量
- **针对的失效**：单次通过就宣布完成，批量使用时崩溃或结果漂移。
- **为什么有效**：三类失效（状态残留、逐项隔离缺失、累积效应）只在"多次/多样"的前提下触发；
  递进结构让每次升级的成本都建立在上一步全绿之上，失败时能把问题域缩小到最近一次升级引入的维度。
- **本项目实证**：2026-09-07 推理验证。Tier-1 单对通过 → Tier-2 第 1 对即整机崩溃（每启动只
  能推理一次的 P0 缺陷），8 月的一次性验收从未暴露它。Tier-3 全量 126/126 通过后才能对性能
  下结论（中位 0.91s/对）。
- **执行要点**：第一级做通核心链路；第二级 ≥3 组且必须包含"上一次失败过的输入"；全量放后台。
- **何时可省**：纯函数级改动且无任何持久状态时，单元层重复执行即可替代。

### T3. 连续运行验证（重复执行；行业检索词：state leak / pass-then-rerun）
- **针对的失效**：进程内持久状态——连接池、锁文件、临时目录、单例、缓存、静态计数器——只在
  **第二次**使用时暴露污染。
- **为什么有效**：它直接构造了失效的触发前提（第二次执行）。第一遍是"功能是否正确"的测试，
  第二遍是"上一遍是否清理干净"的测试，两者检验的是不同的代码性质，后者没有前者不可替代。
- **本项目实证**：EPIPE 崩溃的机理是健康检查在首次长推理期间留下陈旧连接，worker 处理完才
  accept 到它——单次验收永远走不到这条路径。
- **执行要点**：修复类改动必须"同输入连跑两遍"；第二遍的通过标准与第一遍完全一致。

### T11. 故障注入 / 混沌（行业检索词：chaos engineering、fault injection，出处 Netflix Chaos Monkey）
- **针对的失效**：容错代码只在故障真实发生时被执行；"有 try/except"不等于"异常路径正确"。
- **为什么有效**：直接把系统置于故障态观察行为，等价于枚举了故障场景；比代码评审更能发现
  "异常被捕获但处理错误"（如吞掉后进入错误状态）的问题。
- **本项目实证**：entrypoint 监督循环的验证方式就是 `kill -9` worker 进程，观察 8 秒内自动
  拉起、容器存活——比走查 shell 脚本可靠得多（实际上走查就漏掉了 `set -e` 导致循环自杀的问题）。
- **执行要点**：注入点选"依赖进程、网络、磁盘满"三类；每次注入后必须验证**恢复能力**而非仅
  仅是"没崩溃"。

### T10. 浸泡测试（行业检索词：soak testing、endurance testing）
- **针对的失效**：内存泄漏、句柄/文件描述符泄漏、磁盘缓慢增长、日志膨胀——全部随时间线性或
  阶梯增长，短时测试数学上不可见。
- **为什么有效**：泄漏速率 × 时长 > 噪声才能观测，浸泡把时长拉到阈值以上。
- **本项目状态**：未实施。触发条件：出现需要连续运行数小时以上的场景（如定时任务、常驻推理
  服务高频调用）时立项。全量 Tier-3（126 次连续推理）已是其雏形——显存峰值全程稳定 2.26GB
  无增长，即是一次小型浸泡的结论。

## 三、用例设计层技巧

### T6. 等价类划分 + 边界值分析（行业检索词：equivalence partitioning、boundary value analysis）
- **针对的失效**：输入域无限，测试必然是采样；缺陷在边界聚集（off-by-one、空/满、阈值两侧）。
- **为什么有效**：等价类把无限域压缩为有限代表集，解决"测不完"；边界值之所以是优先采样点，
  是因为边界两侧常走不同代码分支（`<` 与 `<=`、空集合与单元素），分支覆盖差异即缺陷密度差异。
- **本项目实证**：推理 `limit` 参数（0=不限，N=前 N 个）与 KML 过滤的空交集路径，都是典型边界。
- **执行要点**：每个数值参数至少取：最小、最小+1、正常值、最大-1、最大、越界各一。

### T7. 数据真实性测试（行业检索词：production-like test data）
- **针对的失效**：代码对数据分布的**隐含假设**（格式唯一、字段必填、编码一致）不会体现在手工
  构造的规整数据里。
- **为什么有效**：真实数据的多样性直接攻击隐含假设；合成数据只会"验证代码实现了作者以为的规格"。
- **本项目实证**：权威 348 条 TBBH 实际存在 C 前缀（143）/ZJ 前缀（119）/CT 前缀（81）/纯数字
  （5）四种格式；用 `Mine.csv` 的编号（非权威源）做搜索必然失败。若测试只用单格式造数，格式
  处理缺陷永远不可见。
- **执行要点**：测试数据从权威资产生成；发现格式分叉时，每个等价类至少一条真实样本进固定用例。

### T8. 异常路径与负面用例（行业检索词：negative testing、error path）
- **针对的失效**：异常分支的代码量与缺陷密度成正比，但用户少走、开发者少测——双重覆盖不足。
- **为什么有效**：异常路径的失败模式（静默吞掉、错误码丢失、状态半更新）无法被正常路径用例触发。
- **本项目实证**：错误密码测试（红色"账号或密码错误"正确显示）；worker 对已断开客户端的响应
  写入失败后**记日志并继续服务**——"明确失败但不伤服务"是异常路径的设计契约。
- **执行要点**：每个外部交互（登录、上传、API 调用）至少三条负面用例：空输入、错误凭证、中断。

### T9. 并发与竞态（行业检索词：race condition、concurrency testing）
- **针对的失效**：竞态的触发依赖特定时序交错，串行测试在概率上永远碰不到。
- **为什么有效**：并发压测把时序交错的概率放大到可观测；竞态一旦在测试中出现，几乎必然可稳定
  复现（时序窗口通常由代码结构决定，不是纯随机）。
- **本项目实证**：miner-api 的 `kmlInferenceActive` 锁使第二个并发推理请求得到明确 409——
  这是"并发时行为可预期"的正例。
- **执行要点**：优先验证"是否有锁/队列"这一结构事实，再决定是否需要压测工具。

## 四、工程与工具层技巧

### T12. 回归墓碑（行业检索词：regression test；红-绿重构的第一步）
- **针对的失效**：修复过的 bug 在重构/回滚/合并中复活——没有测试守卫，复活是静默的。
- **为什么有效**：测试把"bug 曾存在的条件"固化为可执行断言；修复代码被误删时测试变红，等于
  给修复上了保险。这也是 AGENTS.md"先复现定位根因 → 写失败测试 → 最小修复"流程的最后闭环。
- **本项目实证**：EPIPE 修复附带 `test_survives_client_disconnect_before_response`——修复前
  它在旧代码上红（复现 BrokenPipeError），修复后绿。任何人删掉 send 守卫，CI 立即变红。
- **执行要点**：回归测试必须在**未修复的代码上先跑红**，否则它没有证明力（可能永远绿）。

### T13. 环境一致性（行业检索词：test environment parity）
- **针对的失效**：宿主机与部署环境的依赖/内核/文件系统差异，导致"测试通过但部署失效"或相反
  ——测试结论在错误的环境里失去效力。
- **为什么有效**：测试的价值命题是"此处通过 ⇒ 彼处通过"，环境不等价则命题不成立。
- **本项目实证**：worker 的 AF_UNIX socket 测试在 Windows 宿主机结构性不可运行（24 个
  ModuleNotFoundError + AF_UNIX 缺失），而容器内 112 个测试全绿——容器才是权威测试环境，
  宿主机套件仅作冒烟。
- **执行要点**：明确每个测试套件的权威环境并写进文档；平台相关用例用 skipUnless 显式标注。

### T14. 先测量后优化（行业检索词：profiling before optimization；"premature optimization"）
- **针对的失效**：性能直觉在缓存/IO/冷启动面前系统性失准，优化错对象浪费时间还引入风险。
- **为什么有效**：分阶段计时把"慢"分解为可归因的构成，优化对象从猜测变为测量结论。
- **本项目实证**：体感"推理偏久（30~40 秒）"，打点后发现暖跑 inference 仅 3.5s（占 93%）、
  全量中位 0.91s——真正的问题是崩溃导致的反复冷启动，不是 GPU 慢。若无打点，会把优化精力
  错投到批处理/并行上。
- **执行要点**：先加分阶段计时（一次提交的纯增量），跑真实负载拿到分布（中位数比平均值抗
  离群），再决定是否优化、优化哪段。

### T15. 测试中的敏感信息管理
- **针对的失效**：测试日志、截图、CI 输出、临时文件是常被遗忘的泄露面；AGENTS.md 明令禁止
  密码入日志/文档/提交。
- **为什么有效**：泄露面的本质是"敏感值流入了持久化介质"；对策必须逐介质切断（内存变量直用、
  临时文件用后即删、断言只输出布尔/长度不输出内容）。
- **本项目实证**：管理员密码经剪贴板→失败（剪贴板随进程退出清空），改为临时文件→浏览器内存
  变量→`fill()` 注入→立即删除；期间所有校验只输出布尔值，密码零回显。
- **执行要点**：设计涉及凭证的测试时，先画出值的流向图，确认每个落点要么不持久、要么即用即删。

### T16. 工具限制与产品缺陷的隔离
- **针对的失效**：自动化测试失败后直接当 bug 修，浪费工时甚至改坏正确代码；反过来，真缺陷被
  "工具问题"一句话掩盖。
- **为什么有效**：区分两者的判据是**替代路径验证**——换一种驱动方式（坐标点击替代语义点击、
  人工操作替代脚本）若行为正确，则工具嫌疑上升；同时排查应用的可疑构造（全局动画、透明覆盖层）。
- **本项目实证**：Playwright 对全部按钮语义点击超时，但坐标点击、人工交互全部正常，且源码无
  全局动画——结论记为工具限制，未做任何"修复"。
- **执行要点**：结论必须写明证据（做了哪些替代验证）；工具限制要记录在案，避免下次重查。

### T17. 满屏页面滚动验证（overflow 审查）
- **针对的失效**：为全屏地图/大屏设计的全局样式（`html,body{overflow:hidden}` + 100% 高度外壳）
  会让后加的普通页面在内容超过一屏时被**静默裁剪**——不报错、内容不可达、页面不可滚。
- **为什么有效**：滚动缺陷无法靠"页面能打开、数据正确"发现，只有**实际执行滚动动作**才暴露；
  且全局 overflow 样式总是先于内容页存在，属于结构性埋雷，内容一多必然触发。
- **本项目实证**：项目工作台（348 矿山列表）无法滚动（2026-09-08 协作者使用时暴露）；
  根因即 index.html 全局 `overflow:hidden` + `.app-shell height:100vh`，修复为工作台页面
  自带滚动容器（`height:100vh; overflow-y:auto`）。
- **执行要点**：每个独立页面实测"滚到底 + 滚回顶"；把窗口高度调小（如 768px）复测；
  检查点不止"能滚"，还包括"滚到的底部内容完整、可交互"。
- **何时可省**：确认单屏展示、无内容溢出可能的页面。

### T18. 渲染取证：截图失效时的 DOM 状态核验（行业检索词：visual debugging；DOM forensics）
- **针对的失效**：视觉验证依赖截图，但截图后端本身会失真（合成伪影、拼接错位、捕获直接失败）；
  只看截图会把"截图坏了"误判成"页面坏了"，或反过来掩盖真实渲染缺陷。
- **为什么有效**：最终渲染 = DOM 状态 + 浏览器合成。DOM 状态可以程序化取证，绕过合成环节：
  图层元素计数与 src、SVG path 的 `d` 属性长度、`elementFromPoint` 命中测试、把图片/瓦片
  画进 canvas 解码像素均值。逐层比对就能定位"哪一层画错/没画"，比人眼比对截图精确得多。
- **本项目实证**（2026-09-09 离线底图黑屏）：截图全黑，但取证显示瓦片 `img.leaflet-tile-loaded`
  30 张、直连 fetch 200、瓦片像素均值 RGB[59,73,39]（真实植被影像）→ 影像正常，是"被上层盖住"；
  再查遮罩 pane 的 path `d` 仅 33 字符（只剩世界矩形外环）→ 孔洞环丢失 → 锁定坐标轴未翻转。
  另：截图右侧/底部重复条带是捕获合成伪影，DOM 测量（元素矩形）与截图坐标不一致即暴露。
- **执行要点**：截图异常时先 DOM 取证再下结论；canvas/地图类内容必须解码像素验证，
  不能只看元素存在或网络 200；`elementFromPoint` 回答"这一点上最顶层是谁"。

### T19. 测试解释器钉死（行业检索词：test environment parity；interpreter drift）
- **针对的失效**：验证门命令里的裸 `python`/`node` 指向随时间漂移的宿主机环境——新装了别的
  版本、依赖被升级（如 flask_sqlalchemy 3.x 移除 `BaseQuery`）、 PATH 顺序变化。同一命令
  昨天全绿今天报 25 个 import error，看似代码回归实为环境漂移，反向掩盖真回归。
- **为什么有效**：验证门结果 = 代码 × 解释器 × 依赖矩阵 三元乘积；代码不变而其余两项漂移时，
  只有把解释器和依赖钉到与生产一致，门的红绿才只反映代码。
- **本项目实证**（2026-09-09）：同一 `unittest discover` 在宿主机 C:\Python314（无 flask）、
  Python310（flask_sqlalchemy 过新）、Miniconda 三个环境给出三份不同的失败清单；切到与
  镜像一致的 MMSeg310 conda 环境 116 个测试全绿——main 代码从未坏过。
- **执行要点**：验证门文档必须写明解释器来源（绝对路径/容器+环境名）；跨环境出现"不可能的
  失败"时，第一反应是换权威环境复跑，而不是开始改代码。
- **何时可省**：验证门已在容器/CI 内固定解释器运行的项目。

### T20. 悬浮层遮挡与裁剪审查（行业检索词：tooltip occlusion；overlay clipping）
- **针对的失效**：tooltip/popover 等悬浮层跟随鼠标定位，在窄容器（侧栏图表、折叠菜单）里
  溢出到容器外——或压住相邻内容、或被容器边缘裁剪、或盖在地图影像上难以阅读；同时，
  坐标轴标签被截断成「…」会迫使读者依赖悬停读全名，放大悬浮层问题。
- **为什么有效**：悬浮层的默认定位策略通常假设容器足够宽；窄面板 + 长类目名（如
  「复垦责任主体的无主废弃矿山」14 字）是冲突高发组合。判定标准是几何断言而非肉眼：
  tooltip 矩形必须完全落在其宿主图表容器矩形与视口之内。根治优先于补丁——标签直接
  换行可读（信息设计）优于依赖悬停（交互补偿），`confine: true` 兜底防溢出。
- **本项目实证**（2026-09-12 用户报告）：矿端右栏「图斑类型分布」悬停信息框溢出面板、
  压住相邻条目标签；根因是 ECharts tooltip 未设 `confine` + 类目标签 `overflow:'truncate'`
  截断。修复：tooltip `confine: true` + 标签 `overflow:'break'` 换行；回归测试
  `frontend/tests/miner-chart-tooltip.test.mjs` 扫全部图表 × 每根条目断言几何约束
  （实测 24 次悬停全合格）。
- **执行要点**：图表类组件逐条目悬停，断言 tooltip ⊆ 宿主容器 ∧ ⊆ 视口；同时检查标签
  文本是否以「…」结尾（截断迫使悬停）；悬浮层深色底 + 边框保证浮在影像上时可读。
- **何时可省**：无悬浮层的纯静态展示区。

### T21. 自动化直达 vs 用户路径（行业检索词：test path fidelity；UI-bypassing automation）
- **针对的失效**：自动化用底层 API 直达目标（如 setInputFiles 直连 `<input>`、直改路由跳过
  导航按钮），绕过了用户真实操作路径上的每一环——按钮的 click handler、ref 绑定、组件
  通信。这些环节坏了测试照样绿，用户却点不动。
- **为什么有效**：缺陷往往藏在「入口 → 目标」的链路上（本次是组件拆分后父组件 refs
  失联，按钮 handler 静默空转）；直达式自动化把链路短路了，等于只测了链路终点。
  Playwright 的 `waitForEvent('filechooser')` + 真实按钮点击能走完整个链路，同等成本。
- **本项目实证**（2026-09-12 用户报告）：解译平台「选择文件/选择整个文件夹」按钮无效
  ——Segmentation.vue 拆分后 input 移入子组件，父组件 `this.$refs.folderInput` 永远是
  undefined，`if (ref)` 守卫静默吞掉。冒烟测试当时用 setInputFiles 直连 input，全绿
  放行。修复：refs 经子组件桥接（getSourceInput/getCutCheckbox）；冒烟改走
  filechooser 真实路径。
- **执行要点**：涉及「入口控件 → 状态变化」的用例，一律从真实入口控件驱动（点按钮、
  键盘、拖拽），仅把底层注入用于入口之前的预置数据；ref 绑定类回归，真实路径是唯一
  能拦截的测法。
- **何时可省**：纯计算/纯展示逻辑（无交互入口）。

### T22. 宿主机验证 ≠ 镜像内验证（行业检索词：interpreter drift; validation environment parity）
- **针对的失效**：任何「在宿主机跑一遍当验证」的动作，当宿主机与镜像运行时存在版本/
  文件差异时给出假阳性。2026-09-14 一条链上连爆三例：① `write-runtime-env.py` 的
  f-string 嵌套单引号在宿主 Python 3.14 `py_compile` 通过，镜像内 MMSeg310 Python
  3.10 直接 SyntaxError，容器启动即死；② GPU 契约测试断言 HEALTHCHECK 旧参数，
  挂载宿主 backend 跑单测时读到的却是镜像内旧 Dockerfile——断言通过，重建后镜像内
  跑才红；③ 上一条的根源是挂载式验证天然混合环境（宿主 backend + 镜像其它部分）。
- **为什么有效**：T19 已定性"单测必须在镜像解释器跑"，本条是其推论——**py_compile
  /语法级检查也一样**（3.12+ 放行 f-string 嵌套同类引号）；且挂载式容器只替换
  `/app/backend`，凡测试读取 `/app/docker`、`/app/frontend` 等镜像内文件时，测的是
  旧镜像内容。最终验收必须在重建后的镜像容器内全套重跑（本次 140/140 即在那里
  拦下契约测试失配）。
- **本项目实证**（2026-09-14）：修复线四分支挂载验证全绿（backend 140/140），镜像
  重建后容器首启 SyntaxError、二启契约测试失败，各多花一轮重建。防回归：
  `test_jiangxi_gpu_contract.py` 已锁新 HEALTHCHECK 参数；f-string 修复处留有版本
  警示注释。
- **执行要点**：改 `docker/` 下任何被测试引用的文件（Dockerfile/entrypoint/*.py 脚本）
  后，宿主验证只能算冒烟；权威门 = 重建镜像 → 容器内全套单测 + 首启日志人工看一遍。
- **何时可省**：改动与镜像内容完全无关（如纯文档）。

### T23. 共享临时目录的清理契约（行业检索词： temp dir ownership; startup cleanup contract）
- **针对的失效**：一个目录被两个进程/阶段先后使用，后启动的一方按"目录归我"的假设
  清空它，把先到者写的文件吞掉。2026-09-14：kml_roi 推理的 Flask 进程把预处理产物写
  在 per-run `work_dir/preprocess/` 下，而子进程 `pipeline.py:48-49` 启动时
  `rmtree(work_dir)`（防上一轮残留的既有双保险），产物被删，切瓦片报
  `No such file or directory`——单测全绿（fake 子进程不执行 rmtree），只有真实推理暴露。
- **为什么有效**：这类失效的盲区在「跨进程目录所有权」从不体现在任何单测里——fake
  掉子进程就 fake 掉了它的清理行为。防线有二：① 写入方使用**目录所有者之外的独立
  临时目录**（本例 `mkdtemp(prefix="kml-roi-preprocess-")`，生命周期只覆盖自己）；
  ② 契约测试断言"产物路径不在 work_dir 内"（`test_kml_roi_preprocess.py` 已加
  `is_relative_to(work_dir)` 反断言）。
- **本项目实证**（2026-09-14）：prehandle=2 首次真实验证即触发；修复后 baseline /
  prehandle=2 / prehandle=4+denoise=5 / 非法值 400 全场景复验通过。
- **执行要点**：向任何"别人也会用"的目录写入前，先 grep 该目录的全部读写方与清理
  逻辑（rmtree/mkdtemp/cleanup）；两进程共用数据时，各自的数据放各自前缀的独立
  临时目录，只把"只读引用"（路径字符串）跨进程传递。
- **何时可省**：单进程独占的临时目录。

### T24. 验证链对「被修复行为」的隐性依赖（行业检索词：test oracle dependence on bugs；ripple effect of fixes）
- **针对的失效**：验证基础设施（健康检查、冒烟、契约测试）本身依赖着某个 bug 的存在
  才通过——修复该 bug 后验证链反向断裂。2026-09-14 修复夜两连发：① 404 语义修复
  （HTTPException 不再被吞成 200）后容器变 unhealthy——healthcheck 一直探测 backend
  根路径 `/`，靠的正是「404 被吞成 200」才绿；② 同一轮 CRLF 事故：Windows 上以文本
  模式写 shell 脚本引入 ``，shebang 变 `bash` 退出码 127，`bash -n` 与源码断言
  都不查行尾。
- **为什么有效**：这类失效无法从被修模块单测发现——healthcheck 是独立脚本，跑在
  容器编排层。防线：① 探测点必须用**语义化端点**（/api/auth/session 这类业务真实
  存在且区分于 404 的路由），不用根路径这种"碰巧有响应"的位置；② 给验证基建自身
  上守卫（docker/tests 新增 shell 脚本 LF 行尾断言）；③ 修复任何「响应语义」类 bug
  （状态码/错误体）后，必须 grep 全部消费该响应的探测点（healthcheck/监控/curl
  脚本）再重建验收。
- **本项目实证**（2026-09-14）：404 修复 → healthcheck unhealthy（探测点依赖旧
  bug）；改探测点 → 仍 unhealthy（CRLF 杀 shebang）；LF 修复 + 行尾守卫后才绿。
  三连击全部由「重建镜像 → 容器真实验收」拦下，无一带病交付。
- **执行要点**：改 shell 脚本一律二进制/显式 newline="
" 写入；healthcheck 探测
  语义化端点；修复状态码/错误语义类 bug 后全量 grep 消费方。
- **何时可省**：与响应语义、脚本执行无关的纯库函数改动。

### T25. Windows junction 与递归删除穿透（行业检索词：reparse point traversal；symlink-aware cleanup）
- **针对的失效**：给临时 git worktree 用 NTFS junction（`New-Item -ItemType Junction`）
  共享主工作树 `node_modules` 后，任何**穿透型递归删除**（`git worktree remove`、
  `Remove-Item -Recurse`）都会沿 junction 把**目标目录内容整体删掉**——链接不是
  挡板而是通道。2026-09-15 复审修复夜两次发生：`git worktree remove` 清理
  `.worktrees/recheck-*` 时把主树 miner/frontend 的 node_modules 全部删空。
- **为什么有效**：失效发生在"工作区管理"而非任何被测代码里，单测/构建门全绿也
  拦不住；且第一次删除后 junction 指向空目录，后续构建失败表象（模块缺失）与
  根因（链接穿透）相距很远。防线：清理 worktree 前**先枚举 reparse point 并只删
  链接本身**（`cmd /c rmdir <link>` 只摘链接不碰目标），再执行 worktree remove；
  给子代理的任务书里明确禁止其自行 remove worktree。
- **本项目实证**（2026-09-15）：两次删空、两次 `npm ci` 恢复；第二次的诱因是
  bash 双引号吞掉 PowerShell 的 `$_` 变量导致 junction 摘除命令静默变成语法错误、
  `git worktree remove` 照常执行——**跨 shell 拼接命令时先跑只读枚举确认输出**，
  不能假设中间步骤成功。
- **执行要点**：摘链接用 `cmd /c rmdir`（勿用 Remove-Item -Recurse）；枚举用
  `Get-ChildItem -Recurse -Attributes ReparsePoint`；PowerShell 命令经 bash 传递时
  `$_` 必须转义或改用逐条显式路径；并发 `npm ci` 重建期间不要经 junction 跑构建。
- **何时可省**：不使用 junction/符号链接共享依赖目录的仓库。

### T26. 修复声明 vs 实现逐条对照（行业检索词：claim-to-evidence audit；fix verification）
- **针对的失效**：修复提交的信息/注释声称的行为与代码实际行为不符——收口漏改
  （注释说"业务消息走上面的 ValueError 分支"而分支不存在）、透传死键（BFF 读的
  键在子进程输出里从不存在）、守卫失效（语法守卫注释声称能拦实际拦不住）。三类
  都是"声明与实现的接缝"处断裂，且写修复时的测试往往没有覆盖到声明本身。
- **为什么有效**：修复验收通常只验证"改的地方对不对"，不验证"声称的地方全不全"。
  把每条修复声明当作待证命题、沿生产者→消费者两侧重走代码路径并 grep 证据，能
  在合入前暴露缝隙。2026-09-16 第二轮审查的 4 个 P1 中 3 个由此捕获。
- **本项目实证**（2026-09-16）：docs/code-review-20260916.md P1-1/P1-2/P1-3。
- **执行要点**：审查指令里显式要求"对上一轮每条修复声明给出实现证据（file:line）
  或判定不成立"；两个独立代理交叉发现同一问题可视为免复验信号（record_id 双代理
  各自命中）。
- **何时可省**：修复带有行为级测试且主控在目标环境亲跑过门时。

### T27. 语法守卫必须用目标解释器子进程实测+元测试自证（行业检索词：PEP 701；feature_version limitation）
- **针对的失效**：在高版本宿主用 `ast.parse(source, feature_version=(3,10))` 拦截
  语法级回归。PEP 701（3.12）改变了 f-string 的 token 化方式，`feature_version`
  **不会**回退 f-string 文法——3.12+ 宿主对嵌套同类引号 f-string 照样 ACCEPTED，
  守卫注释却声称"高版本宿主也拒绝"，形成守卫自身假绿。
- **为什么有效**：守卫类测试的失效模式是"守卫本身从未被喂过非法样本"。给守卫补
  元测试（喂已知非法 fixture，断言守卫 reject），并让守卫改为子进程调用真实目标
  解释器（Windows `py -3.10`、容器内 `sys.executable`），语法判定就不再依赖宿主
  版本语义。2026-09-16 实测：3.14.4 ACCEPTED、真 3.10.3 SyntaxError、新守卫元
  测试抓到 fixture。
- **本项目实证**：docker/tests/test_write_runtime_env.py（103eb11 修复）。
- **执行要点**：守卫=子进程目标解释器 + 缺解释器时显式 skip 并告警（勿静默 pass）
  + 元测试自证；至少删掉守卫里未经实测的论断性注释。
- **何时可省**：宿主与目标解释器同版本时（此时 ast 直接可判）。

### T28. 同 blob 不同检出 → 门判定分裂；CR 计数假象（行业检索词：autocrlf drift；working tree skew）
- **针对的失效**：`.gitattributes eol=lf` 规则晚于文件首次提交时，老检出（autocrlf
  时代写盘 CRLF）与新检出（规则生效写盘 LF）磁盘字节不同、blob 相同。按磁盘字节
  判定的门（prettier `endOfLine: lf`）于是出现"worktree 绿、主树红"的分裂，漂移
  被误诊为代码问题。2026-09-16：useWeather.js 主树 verify 红、当日新建 r2-miner
  worktree 同文件绿。
- **为什么有效**：先比"同一文件在两个检出的 md5"再下结论，能立刻把问题从代码层
  拨到工作区层。另注意测量假象：bash `$'\r'` 在某些复合命令里被吞成空模式，
  `grep -c ''` 数的是**总行数**，曾据此误判"blob 内嵌 139 个 CR"——空模式计数=
行数，与文件行数相同即应怀疑。
- **本项目实证**：2026-09-16，cp LF 副本刷新主树工作文件后 prettier 立即绿、
  git 视为零变更（内容本来就相同）。
- **执行要点**：行尾判定用 `file`/`od -c` 交叉验证，慎用 `$'\r'` 单证据；修复=
  刷新工作副本（或 `git add --renormalize`），并向后记录哪些历史文件未 renormalize。
- **何时可省**：仓库从初始提交就钉死 eol 且无 autocrlf 历史检出。

### T29. 「死键」裁决前必须 grep 键名本身（行业检索词：dead code detection false positive）
- **针对的失效**：宣布环境变量/npm script/配置键已死时，只 grep 了**旧消费者文件
  名**（geoviewBackend.js 已删 → 认定 GEOVIEW_BACKEND_URL 无消费者），漏掉**新的
  消费者按变量名**读它（authBackend.js/projectBackend.js 第一行 `process.env.
  GEOVIEW_BACKEND_URL`）。compose 部署形态下该键是 miner→Flask 全部转发的唯一
  正确取值来源，删除即登录/项目转发打空。
- **为什么有效**：变量是按名字被读的，判死必须按名字全仓反查（含 services/、
  compose、start 脚本、测试契约）；修复期删除前再取证一次，与审查结论互相独立，
  2026-09-16 修复代理删除前 grep 拦下审查的这条例行"清理项"（审查报告已加更正
  注记）。
- **本项目实证**：docs/code-review-20260916.md P2-16 更正；test_compose_isolation
  已补防误删注释（7f05ab0）。
- **执行要点**：判死三步——`grep -rn "<KEY>"`（名字级）、枚举 `process.env.`/
  `os.getenv` 引用面、检查契约测试是否锁定该键；跨辖区键的清理必须由主控排批次。
- **何时可省**：键有类型化配置层（集中读取、静态可查）时风险较低，仍建议名字级
  grep。

### T30. 验证车辆必须复刻目标运行形态（行业检索词：test environment fidelity；device contract）
- **针对的失效**：两类车辆失配——① 挂载式跑法（宿主代码卷覆盖 /app）遇到
  gRPC-FUSE 目录读抖动，importlib `_fill_cache` 报 `Cannot allocate memory`，
  同一套件一次 1 error 一次全绿，误诊为代码回归；② fresh 容器漏带 `--gpus`/
  `JIANGXI_INFERENCE_DEVICE=cpu` 覆盖时，env 文件钉死的 cuda:0 让设备契约**正确
  拒绝**，5 个推理 API 测试收 400——契约工作正常，门却假红（2026-09-16 终验
  曾据此误判需重查）。
- **为什么有效**：设备的无静默回退契约本来就会把"无 GPU 车辆跑 GPU 配置"变成
  显式失败；把"车辆形态与被测套件的要求匹配"列为跑门前检查项（GPU 测试 → GPU
  车辆或显式 cpu 覆盖且测试不依赖 cuda、单测权威跑 → 种子过的烘焙镜像内 §5 跑法），
  假红即可归因到车辆而不是代码。重复性失败优先怀疑车辆、单次性失败优先怀疑代码，
  本轮两者先后发生且都被此法归因。
- **本项目实证**：2026-09-16 电池——battery 容器（--gpus + 种子卷）191 OK；
  fresh 无 GPU 容器同套件 5 failures（设备 400），补 cpu 覆盖后 191 OK。
- **执行要点**：跑门前核对车辆清单（设备变量、GPU 挂载、种子卷、挂载 vs 烘焙）；
  权威门一律在烘焙镜像 + 完整 entrypoint 初始化的容器里跑；挂载式跑法只作快速
  信号，不作为裁决依据（T22 重申）。
- **何时可省**：纯宿主侧门（miner/npm、docker/tests）无车辆失配问题。

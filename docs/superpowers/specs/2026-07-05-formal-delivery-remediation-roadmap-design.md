# 正式交付包整改路线图设计文档

## 1. 背景与目标

当前目录 `d:\项目\JiangXi\YunNan_prechange_20260703_223508` 已确认不是完整正式仓库，而是“修改前定向备份 + 局部可运行子项目 + 部分离线交付材料”的组合体。现有问题不止是单点代码错误，还包括源码缺失、部署结构不闭合、测试材料缺失、交付文档与实际目录不一致等系统性缺口。

本设计文档的目标不是提出临时救火方案，而是定义一条可连续推进、最终一次性恢复到“正式交付包可验收”状态的整改路线。整改完成后，交付物应同时满足以下两条标准：

- 源码移交标准：源码完整、关键模块齐全、可构建、可测试、文档一致。
- 上线验收标准：部署闭环、服务可启动、核心链路可验证、验收材料齐全。

## 2. 当前状态判断

基于当前项目核查结果，现状可概括为以下几点：

- 当前目录不是完整 Git 仓库，无法追溯正式版本基线。
- 关键业务文件、前端组件、服务路由和测试文件存在缺失。
- `miner` 子项目具备局部前后端雏形，但当前前端构建被阻断。
- 部署文档描述的是完整五服务系统，但当前目录无法支撑文档所述完整部署。
- 已有的局部接口可用现象不能证明当前目录具备独立交付能力。

因此，整改必须从“交付基线重建”开始，而不能直接从页面或接口修补入手。

## 3. 设计原则

- 以正式交付为终点，不采用“先临时修能跑、后面再说”的路线。
- 以阶段化推进控制风险，但阶段之间连续衔接，不做缩水交付。
- 所有调整都以当前已确认缺口为依据，不凭经验假设不存在的源码或部署结构。
- 每个阶段必须有明确输出物和验收点，保证团队可持续推进。
- 优先修复阻断交付的问题，再补齐业务闭环，最后完成测试与文档收口。

## 4. 总体整改策略

推荐采用“分阶段闭环式，一次性修到正式交付标准”的整改策略。

该策略与两种替代方案的区别如下：

- 一次性并行补齐式：理论上速度快，但当前前置依赖多、缺口分布广，返工风险高。
- 最小可运行优先式：能更快看到“跑起来”的结果，但容易把临时修补带入正式交付，后续整理成本更高。
- 分阶段闭环式：先建立交付基线，再恢复最小交付链路，再补齐完整业务闭环，最后完成测试与验收收口，最适合当前项目状态。

## 5. 分阶段整改方案

### 阶段 0：交付基线重建

#### 目标

先确认“什么才是正式交付包”，把当前备份目录与真正交付源码、部署材料、离线资源边界划清。

#### 具体调整方案

- 回到完整源仓库或原始交付来源，确认正式交付范围。
- 对照缺失清单，补齐关键源码、前端组件、服务路由、测试文件。
- 重新梳理目录边界，统一 `backend`、`frontend`、`miner`、`offline_bundle`、部署配置与数据资源位置。
- 明确哪些内容属于正式交付，哪些只是备份辅助材料。

#### 输出物

- 正式交付目录清单
- 缺失文件回补结果
- 交付边界说明
- 统一后的源码与部署结构

#### 验收点

- 关键缺失文件不再缺位。
- 目录结构与后续部署文档一致。
- 团队能够明确指出“哪一份目录是正式交付源”。

### 阶段 1：最小可交付链路恢复

#### 目标

恢复“可构建、可启动、可验证基础接口”的最小交付能力。

#### 具体调整方案

- 修复 `miner/src/App.vue` 的前端构建阻断问题。
- 修复 `miner/server.js` 中明显的运行时风险，例如未定义变量和悬空依赖。
- 对齐前端入口、后端入口、Vite 代理、端口和 API 基础路径。
- 修正部署编排与实际源码路径不一致的问题，让最小启动链路成立。

#### 输出物

- 前端构建成功
- 后端启动成功
- 最小 API 可访问
- 基础部署入口可执行

#### 验收点

- `npm run build` 成功。
- 后端关键接口可返回有效数据。
- 启动验证不依赖本机历史残留服务。

### 阶段 2：完整业务链路补齐

#### 目标

从“能跑”升级到“核心业务可闭环验收”。

#### 具体调整方案

- 补齐 GeoView 与 Miner 的关联链路。
- 补齐矿区数据、属性数据、变化矩阵输出、KML ROI 推理、离线地图资源之间的关系。
- 对齐前端页面展示、详情面板、图层加载、跳转与导出能力。
- 补齐后端接口与数据文件约定，确保输入输出格式稳定。

#### 输出物

- 端到端主流程闭环
- 关键页面可操作
- 样例数据可复现
- 数据链路说明文档

#### 验收点

- 从数据输入到页面展示至少走通一条完整主链路。
- 变化矩阵、详情查询、地图展示、联动跳转等核心能力都有验证结果。

### 阶段 3：测试、文档、验收收口

#### 目标

把“技术可运行”提升到“正式可交付”。

#### 具体调整方案

- 补齐自动化测试或最小冒烟测试。
- 重写部署文档、环境变量说明、启动步骤、验收步骤和故障排查说明。
- 统一版本说明、交付清单、验证地址和验收口径。
- 校准 healthcheck、运行检查项、样例数据和验证结果说明。

#### 输出物

- 测试基线
- 正式部署文档
- 验收清单
- 版本与交付说明

#### 验收点

- 新环境按文档可独立完成部署。
- 验收人员不依赖开发口头解释即可完成检查。
- 代码、文档和运行结果保持一致。

## 6. 模块任务映射

### 6.1 仓库与源码基线

- 从完整源仓库重新整理正式交付目录，不再直接以当前备份目录作为最终交付源。
- 补齐缺失文件，重点包括 `backend/applications/...`、`miner/routes`、`miner/services`、`miner/src/components` 以及历史测试文件。
- 建立源码清单与交付清单映射，明确哪些内容属于正式交付，哪些属于备份痕迹或辅助材料。

### 6.2 后端模块

- 梳理 Python 后端与 Node 后端的职责边界。
- 修复 `miner/server.js` 的运行时问题，统一接口输入输出契约。
- 校验 `backend` 目录下的模块引用，清理悬空导入与缺失实现。
- 统一 API 清单、错误返回、依赖数据路径与运行时配置。

### 6.3 前端模块

- 修复 `miner` 当前构建错误。
- 校正页面依赖的数据结构与后端返回结构。
- 补齐缺失页面组件，重点覆盖地图展示、工作台、详情面板等模块。
- 梳理 GeoView 与 Miner 的页面职责和联动入口。

### 6.4 部署与环境模块

- 让 `docker-compose.prod.yml`、目录结构、环境变量说明保持一致。
- 补齐根目录缺失的 `config.yaml`、`docker/`、`frontend/` 等交付关键资源，或重构部署方案使其与实际交付结构一致。
- 核查离线镜像包、地图资源挂载、卷映射和 healthcheck。
- 明确干净环境部署步骤，禁止复用未知已运行服务作为验收依据。

### 6.5 测试与质量模块

- 补回历史测试或建立最小替代测试集。
- 最低覆盖要求包括：前端构建、后端启动、关键 API、核心业务主链路、部署健康检查。
- 建立交付前检查项，如构建通过、接口冒烟通过、关键页面验证通过、文档复核完成。

### 6.6 文档与验收模块

- 重写 README 或正式交付说明，不再使用备份说明代替正式说明。
- 整理部署文档、样例数据说明、接口说明、页面说明、版本说明。
- 建立验收清单，覆盖服务启动、页面访问、接口通路、数据链路、离线地图和异常处理。

## 7. 更新计划

### 第 1 波：基线锁定

- 完成交付目录重建
- 完成缺失清单回补确认
- 完成源码来源对齐与正式交付范围确认

退出条件：团队内部对整改对象和正式交付源有唯一口径。

### 第 2 波：基础链路恢复

- 修复前端构建阻断
- 修复后端启动阻断
- 修正部署入口与目录不一致问题

退出条件：干净环境可完成最小启动验证。

### 第 3 波：业务闭环补齐

- 补齐数据链路、页面链路、GeoView/Miner 联动
- 补齐离线地图与变化矩阵相关能力
- 形成端到端业务演示路径

退出条件：至少一条完整业务主流程可复现。

### 第 4 波：交付收口

- 补齐测试、文档、验收清单、版本说明和排障说明
- 形成最终正式交付包

退出条件：新环境可独立部署并通过验收清单。

## 8. 风险与应对

- 无法拿到完整源仓库：立即升级为项目级风险。如果没有完整源仓库，只能退回“当前备份最小可运行恢复”，不能承诺正式交付包恢复。
- 缺失文件过多导致恢复成本超预期：先按 P0 清单做完整盘点，区分必须回补项和可裁剪项。
- 本机已有运行服务干扰判断：所有验收必须在干净环境或隔离容器环境中重跑。
- 文档与代码反复不一致：阶段 0 建立最小边界说明，阶段 3 再统一正式文档。

## 9. 成功标准

- 源码层面：关键模块齐全，目录清晰，可构建，可测试。
- 运行层面：前后端服务独立启动成功，关键 API 可访问，核心页面可用。
- 业务层面：至少一条核心业务链路端到端打通。
- 交付层面：新环境按文档可复现部署与验收。
- 管理层面：团队清楚每一阶段完成了什么、剩余什么、何时可进入下一阶段。

## 10. 结论

当前项目的核心问题不是单点功能故障，而是正式交付基线缺失。最合理的整改方式不是做零散补丁，而是先重建交付基线，再连续推进代码、部署、测试和文档整改，最终一次性恢复到正式交付包可验收标准。

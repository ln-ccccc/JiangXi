## 3. 目标

本次设计目标是把当前系统从“云南历史业务库”切换为“江西空库重建后的首批展示版本”，满足以下条件：

- 运行库中不再保留旧云南项目数据
- `project*` 和 `analysis` 表被清空并重建为江西口径
- 登录后工作台默认展示江西项目，而不是云南历史项目
- 工作台的矿山主体列表来自 `Mine.csv` 聚合结果
- 详情页可以下钻查看图斑明细
- 浏览器主流程不再出现 `云南 / 大理 / 曲靖 / 昆明`
- 保持现有登录、项目 API、工作台和地图基础路由可用

## 4. 非目标

本次设计不包含以下内容：

- 不新增多省动态切换能力
- 不在本轮完成镜像瘦身与单镜像交付
- 不在本轮补齐 `Mine.csv` 之外的所有江西源数据
- 不在本轮实现完整的矿种编码字典治理
- 不在本轮保留云南与江西双数据并存模式

## 5. 方案对比

### 5.1 方案 A1：主体矿山聚合 + 图斑明细下钻

做法：

- 清空 `project*` 和 `analysis`
- 读取 `Mine.csv`
- 以 `主体编号` 为聚合键，生成矿山主体视图
- 创建一个江西默认项目
- 在工作台列表中展示江西默认项目
- 项目详情中展示主体矿山列表
- 在主体或项目详情中展示该主体对应的图斑明细

优点：

- 与当前项目工作台模型最兼容
- 不会把 `383` 条图斑直接平铺在首页
- 保持产品层级清晰，便于后续扩展

缺点：

- 需要增加一层聚合和详情映射逻辑

### 5.2 方案 A2：纯图斑级重建

做法：

- 清空后直接按图斑构造列表和绑定关系

优点：

- 导入链路最直接

缺点：

- 同一主体会重复出现
- 工作台会退化成细碎明细表
- 不适合作为正式交付版的首批江西业务入口

### 5.3 方案 A3：仅做统计看板

做法：

- 清空后只展示汇总统计，不重建项目和主体明细

优点：

- 实现最快

缺点：

- 不满足“系统里要展示江西数据”的主流程要求
- 无法替换现有项目工作台的业务入口

### 5.4 结论

本次实施采用 `A1`，即“主体矿山聚合为主，图斑明细下钻为辅”。

## 6. 总体设计

### 6.1 清库策略

本轮清理目标仅限当前项目目录运行库，不触碰外部源目录。

需清理的表包括：

- `analysis`
- `project`
- `project_mine_binding`
- `project_dataset`
- `project_activity_log`
- `project_export_record`
- `project_backup_record`

不清理的内容包括：

- 管理员账号与认证逻辑
- 代码文件
- `D:\项目\YunNan`
- `D:\项目\江西数据`

清库动作应作为一个显式的初始化步骤执行，而不是夹在普通请求处理中隐式触发。

### 6.2 江西默认项目

清库后，系统应自动重建一个江西默认项目，作为工作台首屏入口。

建议固定字段如下：

- 项目名称：`江西矿山生态修复监测项目`
- 区域：`江西省`
- 管理员：`admin`
- 状态：`active`
- 备注：`system_seed:jiangxi_mine_csv`

监测时间建议采用文件内可推导范围：

- `monitor_start_year`：优先取 `关闭年度` 中最小有效年份
- `monitor_end_year`：优先取 `填报日期` 或 `完成时间` 对应的最大有效年份

如果字段解析失败，则回退为安全固定值，并在导入报告中记录。

### 6.3 展示层级

首批江西展示采用两级结构：

- 一级：主体矿山聚合列表
- 二级：图斑明细下钻

一级列表用于工作台和项目详情概览，二级明细用于主体详情或项目细节展示。

## 7. 数据映射设计

### 7.1 主体聚合键

`主体编号` 作为首选聚合键。

原因：

- 该字段在当前文件中具备较强业务语义
- 可以把多图斑归并到同一主体矿山下
- 比直接用 `矿山位置` 更稳定

若个别记录 `主体编号` 缺失，则该记录应被记录为异常并跳过，不能无规则拼接出新的主体键。

### 7.2 项目绑定表映射

当前系统的项目绑定表为 `project_mine_binding`，可承载主体级摘要。

映射规则如下：

- `project_id`：指向江西默认项目
- `mine_fid`：为每个主体生成稳定整数 ID
- `mine_name_snapshot`：优先使用 `矿山位置`
- `city_snapshot`：使用主体主值 `地市`
- `area_snapshot`：主体下 `Area` 聚合总和
- `status_snapshot`：主体下修复状态摘要
- `sort_order`：按地市、区县、主体编号或面积规则生成

### 7.3 图斑明细字段

首批图斑明细保留以下字段进入展示或接口输出：

- `图斑编号`
- `修复图斑编号`
- `图斑小类`
- `修复状态`
- `修复模式`
- `完成时间`
- `Area`
- `未治理面积`
- `中心经度`
- `中心纬度`
- `关闭年度`
- `图斑属性`

### 7.4 暂不作为首版主展示字段

以下字段先保留在导入原始上下文中，但不作为首版主页面核心字段：

- `填报人`
- `填报单位`
- `备注`
- `矿种`
- `开采方式`

原因：

- `填报人` 涉及个人信息，首版不宜默认前台展示
- `备注` 文本不规整，适合详情补充
- `矿种`、`开采方式` 当前仍是编码或弱语义值，未做字典治理前不适合直接做主筛选

## 8. 接口与存储设计

### 8.1 复用现有项目接口

尽量复用现有项目域 API：

- `/api/projects`
- `/api/projects/<id>`
- `/api/projects/<id>/mines`
- `/api/projects/<id>/timeline`

目标不是推翻现有接口，而是让这些接口在清库和重建后自然返回江西数据。

### 8.2 明细数据存放策略

主体聚合可以直接落在 `project_mine_binding`。

图斑明细需要单独设计存放位置。为了避免把图斑明细硬塞进现有绑定表，建议新增一张江西导入明细表，专门承载主体与图斑的关系及展示字段。

建议新增表的职责：

- 记录 `主体编号` 与 `mine_fid` 的映射
- 记录每个主体下的图斑明细
- 为工作台详情、导出与后续地图适配提供统一来源

该表命名可在实施阶段确定，但职责必须单一且清晰。

### 8.3 导入报告

建议在导入完成后生成一份结构化导入摘要，至少包括：

- 导入文件路径
- 原始记录数
- 成功导入图斑数
- 成功聚合主体数
- 跳过记录数
- 异常记录摘要
- 生成项目 ID

这份摘要既可用于日志，也可写入项目活动日志，作为系统内可追踪的初始化记录。

## 9. 执行顺序

建议实施顺序如下：

1. 新增江西空库重建脚本或服务入口
2. 清空 `analysis` 和 `project*` 相关表
3. 读取 `Mine.csv` 并做字段规范化
4. 以 `主体编号` 聚合，生成主体摘要
5. 创建江西默认项目
6. 写入主体绑定记录
7. 写入图斑明细记录
8. 写入初始化活动日志和导入摘要
9. 复跑项目 API 和浏览器验收

## 10. 错误处理

### 10.1 输入错误

以下情况应直接失败并终止导入：

- `Mine.csv` 不存在
- 编码无法读取
- 缺失关键字段：`主体编号`、`地市`、`区县`、`矿山位置`、`Area`

### 10.2 行级异常

以下情况可跳过单行，但必须记录：

- `主体编号` 为空
- `Area` 不能转为数值
- 经度纬度不合法

### 10.3 聚合冲突

同一 `主体编号` 若出现以下冲突，应记录告警：

- 地市不一致
- 区县不一致
- 主体位置文本不一致

冲突处理规则：

- 聚合主值默认取组内首条
- 其余冲突值写入导入摘要或活动日志

## 11. 测试与验收

### 11.1 自动化验证

至少补充以下测试：

- 清库后 `/api/projects` 不再返回云南项目
- 导入 `Mine.csv` 后 `/api/projects` 返回江西默认项目
- 聚合结果中的主体数量与预期一致
- 典型主体可以返回对应图斑明细

### 11.2 浏览器验收

浏览器验收应至少覆盖：

- 登录后只出现江西默认项目
- 工作台不再出现 `云南 / 大理 / 曲靖 / 昆明`
- 主体矿山列表来自江西数据
- 主体详情能看到图斑明细

### 11.3 通过标准

只有同时满足以下条件，才可判定本轮通过：

- 旧云南项目数据已被清空
- 江西默认项目成功建立
- 工作台列表稳定显示江西主体数据
- 浏览器主流程中不再出现云南默认口径

## 12. 风险与边界

- `Mine.csv` 当前只有一个文件，后续若用户希望加入更多 `csv`，需要新增映射设计
- `矿种` 与 `开采方式` 暂未做字典治理，首版不应把它们作为主筛选入口
- `/api/geojson` 当前为空，本轮核心目标是先完成工作台数据闭环；若要进一步把图斑明细联动到地图面数据，需在实施阶段确认现有地图数据入口是否可直接复用
- 清库是不可逆业务动作，执行前必须只作用于当前运行库，而不能误触外部目录或源数据文件

## 13. 结论

本次应采用“江西空库重建”的方式，而不是继续修补云南历史库。

具体落地策略为：

- 清空当前运行库中的 `analysis` 与 `project*`
- 仅使用 `D:\项目\江西数据\Mine.csv` 作为首批江西业务数据源
- 创建一个江西默认项目
- 以 `主体编号` 聚合构建主体矿山列表
- 以图斑明细作为下钻层
- 通过现有项目 API 和工作台完成江西首批展示闭环

该策略既满足“直接清空云南数据”的要求，也满足“系统里必须展示江西数据”的交付目标。

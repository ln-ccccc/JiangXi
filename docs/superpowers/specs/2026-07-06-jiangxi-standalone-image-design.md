# 江西单镜像交付设计文档

## 1. 背景

当前项目目录 `D:\项目\JiangXi\YunNan_prechange_20260703_223508` 已经完成以下关键工作：

- 正式交付包恢复
- 江西区域化代码改造
- 江西空库重建与业务数据导入
- `/api/geojson` 切换到江西面图斑源

现阶段系统已基本具备江西版业务闭环能力，但运行方式仍沿用当前多容器结构：

- `backend`
- `frontend`
- `miner-api`
- `miner-web`
- `mysql`

并通过 `docker compose` 编排启动。

用户已明确提出新的交付要求：

- 需要把江西项目新打包成一个单独镜像
- 该镜像不是普通应用镜像，而是“应用 + 数据库”的单镜像
- 对外只保留业务访问端口，不继续暴露全部内部端口

因此，这一轮设计目标不再是继续做业务江西化，而是把当前江西版系统封装为一个独立可交付的单镜像运行时。

## 2. 用户已确认约束

本轮已确认的关键约束如下：

- 镜像类型：`应用 + 数据库` 单镜像
- 交付对象：江西项目专用镜像，而不是泛化多省平台镜像
- 对外端口策略：只保留业务端口
- 推荐对外端口：`4000` 和 `5008`
- 不要求继续对外暴露：`3000`、`8000`、`3307`
- 镜像启动后应能直接运行江西版，而不是还依赖外部单独的 MySQL 容器

## 3. 目标

本次设计目标是构建一个“江西项目单镜像交付物”，满足以下要求：

- 单个镜像内同时运行 MySQL 与江西版应用服务
- 启动后可直接访问江西版业务页面
- 启动后数据库自动可用，不依赖外部 MySQL
- 首次启动即可完成江西初始化数据准备
- 仅对外暴露业务端口 `4000`、`5008`
- 内部服务端口 `3000`、`8000`、`3306/3307` 不对宿主暴露
- 维持当前江西业务口径，包括：
  - 江西默认项目
  - 江西导入数据
  - 江西面图斑 `GeoJSON`

## 4. 非目标

本次设计不包含以下内容：

- 不把项目抽象成通用多省单镜像产品
- 不在本轮重构全部应用为单进程架构
- 不在本轮做 Kubernetes 或 Helm 交付
- 不在本轮做数据库高可用或主从方案
- 不在本轮保留云南与江西双运行模式

## 5. 当前运行结构事实

### 5.1 现有应用镜像

当前运行时基于应用镜像 `geoview-runtime:*`，然后通过不同 entrypoint 分别启动：

- `docker/start-backend.sh`
- `docker/start-frontend.sh`
- `docker/start-miner-api.sh`
- `docker/start-miner-web.sh`

数据库则通过独立 `mysql` 容器运行。

### 5.2 当前对外端口

当前 `compose` 结构中暴露的端口包括：

- `5008`：后端 API
- `3000`：主前端
- `8000`：miner API
- `4000`：miner web
- `3307`：MySQL

这不符合当前用户期望的“只保留业务端口”。

## 6. 方案对比

### 6.1 方案 1：江西单镜像内置 MySQL + 4 个应用进程

做法：

- 新建一个江西专用单镜像
- 镜像内包含：
  - MySQL
  - backend
  - frontend
  - miner-api
  - miner-web
- 使用统一入口脚本在一个容器中拉起全部进程

优点：

- 完全符合“应用 + 数据库单镜像”目标
- 对交付用户来说最简单
- 便于形成江西项目专用镜像标签

缺点：

- 容器内多进程编排复杂度提高
- 健康检查与退出策略需要自己实现

### 6.2 方案 2：江西专用应用镜像 + 外部数据库快照

做法：

- 只做江西应用镜像
- 数据库仍外置

优点：

- 更符合传统 Docker 最佳实践

缺点：

- 不符合用户已确认的“应用 + 数据库单镜像”

### 6.3 方案 3：对当前运行环境做快照封箱

做法：

- 直接基于当前容器和运行态做封箱镜像

优点：

- 速度快

缺点：

- 可复现性差
- 维护成本高
- 难以审计和升级

### 6.4 结论

本轮采用 `方案 1`，即“江西单镜像内置 MySQL + 4 个应用进程 + 只暴露业务端口”。

## 7. 总体设计

### 7.1 镜像职责

新镜像应承担以下职责：

- 容器内初始化并启动 MySQL
- 等待数据库可连接
- 初始化应用运行环境
- 启动 Flask backend
- 启动主前端静态服务
- 启动 miner API
- 启动 miner web
- 对外提供江西版业务入口

### 7.2 对外端口策略

单镜像仅对外暴露：

- `4000`：江西工作台与矿山业务入口
- `5008`：后端 API 与验收接口入口

以下端口仅保留容器内访问，不向宿主暴露：

- `3000`
- `8000`
- `3306`

### 7.3 容器内服务关系

容器内逻辑关系如下：

- `mysqld` 为底座服务
- `backend` 依赖 `mysqld`
- `frontend` 依赖 `backend`
- `miner-api` 依赖 `backend`
- `miner-web` 依赖 `miner-api`

虽然这些服务仍然以多进程形式存在，但从交付视角看，用户只操作一个容器。

## 8. 启动链设计

### 8.1 启动顺序

建议按以下顺序启动：

1. 初始化 MySQL 数据目录
2. 启动 `mysqld`
3. 等待数据库健康
4. 初始化应用运行环境
5. 启动 `backend`
6. 启动 `frontend`
7. 启动 `miner-api`
8. 启动 `miner-web`

### 8.2 统一入口脚本

应新增一个江西单镜像专用入口脚本，例如：

- `docker/start-jiangxi-standalone.sh`

该脚本负责：

- 启动并守护多个进程
- 统一处理失败退出
- 在首次启动时触发江西数据初始化

### 8.3 进程守护

入口脚本需具备以下能力：

- 任一关键进程异常退出时，容器整体退出
- 将主要进程日志输出到标准输出
- 在容器停止时能正确终止子进程

本轮不要求引入复杂的 `supervisord`，但允许采用轻量级 shell 进程守护策略。

## 9. 数据初始化设计

### 9.1 数据库初始化

单镜像首次启动时，需要自动完成：

- MySQL 启动
- 业务库存在性校验
- 表结构初始化
- 管理员账号初始化

### 9.2 江西业务初始化

镜像首次启动后，还需要继续完成：

- 执行江西空库重建导入
- 从 `D:\项目\江西数据\Mine.csv` 重建江西默认项目数据
- 加载江西面图斑源

由于单镜像交付不应继续依赖宿主上的外部数据目录，因此需要明确两种策略之一：

- 将首批江西运行所需数据打进镜像
- 或在镜像启动时挂载一个江西数据目录

本轮推荐优先采用“必要数据打进镜像”的方式，避免交付时还要求用户手工准备一整套路径。

### 9.3 面图斑数据源

当前已确认江西面图斑有效来源为：

- `D:\项目\江西数据\348个图斑.shp`

因此，单镜像需要把这组面图斑相关文件一并纳入镜像，至少包括：

- `.shp`
- `.dbf`
- `.shx`
- `.prj`

并把 `/api/geojson` 默认源改成镜像内部路径。

## 10. 镜像内容裁剪

### 10.1 必留内容

单镜像至少保留：

- `backend`
- `frontend`
- `miner`
- `docker` 启动脚本
- 运行期所需 Python / Node 环境
- 江西初始化所需的 `Mine.csv`
- 江西面图斑源 `348个图斑.*`

### 10.2 可裁剪内容

可在实施阶段评估并裁剪：

- 与云南默认口径绑定的无关交付残留
- 恢复快照与非交付文档
- 非运行时必需的测试夹具
- 不影响江西运行的冗余开发文件

### 10.3 不在本轮深度裁剪的部分

本轮不强制要求：

- 深度拆除所有历史模型资源
- 重构 Conda/Node 环境层
- 极致优化镜像体积

本轮优先级仍是“先形成可运行的江西单镜像”，镜像瘦身只做必要裁剪。

## 11. 配置设计

单镜像对外保留的环境变量应尽量最小化，建议包括：

- `ADMIN_USERNAME`
- `ADMIN_PASSWORD`
- `SECRET_KEY`
- `FRONTEND_PORT`（默认容器内 `3000`）
- `MINER_FRONTEND_PORT`（默认对外 `4000`）
- `BACKEND_PORT`（默认对外 `5008`）

不再要求用户手工提供：

- 外部 MySQL 主机配置
- 外部 `MINER_DEFAULT_KMZ_PATH`
- 外部江西数据目录路径

因为这些应在单镜像内被固定为江西版默认口径。

## 12. 验收标准

单镜像交付完成后，应满足以下标准：

- `docker run` 单个镜像即可启动整套江西版系统
- 宿主只需要访问：
  - `4000`
  - `5008`
- 登录后进入江西工作台
- `/api/projects` 返回江西默认项目
- `/api/geojson` 返回江西面图斑
- 浏览器主流程不再出现云南口径
- 不依赖外部单独 MySQL 容器

## 13. 风险与边界

- 单容器多进程会提高启动脚本复杂度
- 数据初始化若做成“每次启动都导入”，会带来性能和幂等风险，因此必须设计为“首次初始化”或“显式刷新”
- 若把江西数据文件打进镜像，镜像体积会继续增加
- 若后续继续要求更小内存与更小体积，应在本设计落地后进入下一轮专项瘦身

## 14. 结论

本次应新增一个江西专用单镜像交付物，而不是继续依赖现有多容器 `compose` 结构作为最终交付形态。

落地策略为：

- 新建江西专用镜像
- 镜像内置 MySQL 与四个应用进程
- 仅暴露 `4000`、`5008`
- 把江西初始化数据和江西面图斑打进镜像
- 通过统一入口脚本完成数据库启动、业务初始化与应用拉起

该设计可以把当前已经完成的江西化成果，进一步固化为一个可独立运行、可单独交付的江西项目镜像。
